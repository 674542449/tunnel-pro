# tunnelX v0.3：五方案对比与选择

2026-10-02 凌晨，中国标准时间。Windows amd64 → `146.56.99.255:8443`。保留 TLS 1.3、ECH、目标证书验证及现有服务端；五组均使用严格隐私配置。

选择 **E：H2 四连接池 + 快速健康检测 + 温和轮换 + H3 备用**。新版客户端已经在本机运行，默认自动模式：TCP 优先 H2，UDP 优先 H3。它对本次卡住连接的恢复明显更快，下载吞吐保持可用。此选择适用于本次线路和指标，并非所有网络上的绝对最优。

## 五个方案与结果

速度为同一受控 HTTPS 文件的三次 64 MiB 单下载中位数，包含连接和首字节等待；四路并行是另一次 4×16 MiB 测量。恢复时间为通过本地转发器施加故障后，首次完成正常 HTTPS 小请求的时间，包含应用 TLS 和响应读取。故障没有作用于其他程序。

| 方案 | 设置 | 单下载中位数 MB/s | 四路并行 MB/s | 已有 TCP 卡住 | TCP 中断、UDP 可用 | UDP 中断、TCP 可用 | 分数 |
|---|---|---:|---:|---:|---:|---:|---:|
| A | 单连接 H2，旧健康检测设置 | 35.26 | 34.39 | 30.64 秒 | 8.27 秒 | 0.27 秒 | 80.07 |
| B | H2 四连接池，旧健康检测设置 | 24.50 | 42.72 | 29.76 秒 | 8.27 秒 | 0.27 秒 | 72.05 |
| C | H2 四连接池，快速检测、一次新连接重试、120 秒轮换 | 24.73 | 38.06 | 4.44 秒 | 8.35 秒 | 0.27 秒 | 78.78 |
| D | 纯 H3 / QUIC | 11.03 | 7.72 | 0.27 秒 | 0.27 秒 | 10.66 秒 | 74.14 |
| **E** | **H2 四连接池，快速检测、120 秒轮换、H3 备用** | **24.84** | **21.25** | **4.35 秒** | **4.36 秒** | **0.27 秒** | **81.97** |

TCP / UDP 中断持续 8 秒；“已有 TCP 卡住”只阻塞已建立的 TCP 连接，新 TCP 和 UDP 连接仍能正常转发。A / B 的约 30 秒等待与原先 25 秒空闲检测加 5 秒 PING 超时一致。这复现了客户端层面的等待机制，不能据此认定运营商制造了实际故障。

单连接 H2 的单下载中位数最高，四连接池 B 的并行峰值最高；单纯增加连接没有解决缓存坏连接的问题。C 可以快速换新 H2，但 TCP 路径整体不可用时仍需等路径恢复。D 对 TCP 故障不敏感，但同一 QUIC 连接的三次下载从 27.50、11.03 降到 7.05 MB/s，且 UDP 中断后恢复更久。E 使用健康 H2 时保持 H2；TCP 确认失效后可用 H3 建立新业务请求。

所有方案的连续测试小请求成功率均为 100%，E 的综合分数仅比 A 高约 1.9 分。选择 E 主要是减少长时间等待，而不是宣称它的峰值下载最快。

## 方法及选择规则

- 15 次单下载：每组 3 次，使用不同顺序交错进行；64 MiB 完整文件 SHA256 为 `f8dfeaaa09d17ea0e07bcd70bdbf38d55406a6099c6a263a0a27e8e313f12067`。
- 每组一次四路并行完整分段下载，同时发起小型 HTTPS 请求，记录有下载负载时的响应时间。
- 每组约 130 秒持续测试，每 15 秒进行 4×4 MiB 下载，其间与并发期间发送小请求。共 260 次常规小请求、164 次下载并发期间的小请求，以及每组 9 次下载波次，全部完成并验证完整性。
- 每组一次 NTriver 32 MiB ISO 样本。使用此前同一代表性文件及已上线的源站地址偏好，验证 HTTP 206、范围和样本 SHA256。五组都通过，速度分别为 A 4.14、B 13.63、C 16.04、D 4.04、E 3.07 MB/s；这些单次外部源站数据波动很大，不用于单独判定赢家。
- 最终实现对每组重复三种故障场景。转发器只监听本机随机回环端口，真实 WAN 加密连接仍到测试服务器；不改系统防火墙、DNS、全局 TCP 参数或其他程序的连接。

参加排名要求：常规小请求成功率至少 98%，正常下载和并发小请求全部通过，三种故障都能恢复。评分为 40% 小请求成功率、25% 三种故障恢复表现、25% 相对单下载中位数、10% 相对小请求 p95。恢复部分以 30 秒、8 秒、8 秒为归一化上限，超过上限的场景得零分。分数是本次取舍规则，不是标准化 QoS 或抗封锁评分。

[最终原始对比](five-plan-comparison-v0.3.json)、[原始性能与初轮故障记录](five-plan-initial-v0.3.json)、[最终故障复测](five-plan-recovery-final-v0.3.json)。正常下载阶段的数据量约 2.26 GB；已有用户应用仍在运行，背景流量、顺序和线路变化会影响结果。

初轮恢复使用更激进的淘汰逻辑。最终增加 PING 确认，保护正常连接上的其他下载，随后重复全部故障测试；最终表格使用这些复测结果。正常路径没有触发超时分支，保留原始吞吐测量。TCP 与 UDP 故障均纳入最终评分，避免只对 TCP 施加故障而偏向 H3。

## 胜出实现与实际程序复测

配置为 `auto`、TCP 优先 `h2`、目标 H2 连接数 4、建立请求超时 2 秒、空闲检测 5 秒、PING 超时 2 秒、连接年龄 120 秒。E 不先重试新的 H2 连接；确认 TCP 传输失效后直接尝试 H3，保留相同隐私要求。

请求建立超时先用 PING 检查外层连接。如果 PING 正常，保留这条连接，避免把单个源站慢响应误判为整个连接失效。PING 失败才淘汰连接；新请求可选另一种传输。轮换只让旧连接停止接收新请求，已经开始的业务流继续传输。连接总数有上限。详情见 [v0.3 规范](PROTOCOL-v0.3.md)。

真实 Windows EXE 在独立端口完成 TCP / UDP、检测后业务请求、重复启动及 ISO 哈希验证；32 MiB ISO 样本为 **12.70 MB/s**。[程序验收](acceptance-windows-startup-v0.3.json)、[自动分流](acceptance-auto-client-v0.3.json)、[样本](performance-ntriver-new-client-v0.3.json)。

本机已从旧版切换到 `dist/windows-client-v0.3/tunnelx-client.exe`，保留当前 Windows 代理设置及退出时恢复的原始备份。[切换记录](activation-v0.3.json)。切换后同一 ISO 样本三次为 **13.07、10.16、13.13 MB/s**，SHA256 均与之前一致：[第一次](performance-selected-active-iso-1-v0.3.json)、[第二次](performance-selected-active-iso-2-v0.3.json)、[第三次](performance-selected-active-iso-3-v0.3.json)。这确认外部源站单次 3.07 MB/s 并非固定上限。

## 回归及边界

- [线上 16 项验收](acceptance-selected-v0.3.json)全部通过：普通 / 严格模式 H2 与 H3、明确鉴权拒绝、私网目标拒绝、证书和 ECH 拒绝不降级、TCP 不可用时 H3 回退。
- `go test -race -tags=http2legacy ./... -count=1 -timeout 120s` 与 `go vet -tags=http2legacy ./...` 通过；Windows 客户端、验收工具和五方案工具已构建。
- 新增测试验证轮换不打断活跃业务、坏连接只在写入业务数据前重试、慢源站和调用方取消不淘汰正常连接、鉴权拒绝不触发重试。
- [服务端清理](cleanup-five-plans-v0.3.json)确认临时 64 MiB 文件删除，Caddy 原配置按 SHA256 恢复；生产 tunnelX 没有重启。[服务健康](server-health.json)正常，线上二进制仍是 v0.2.1 构建，客户端兼容。
- 下载片段完整性通过不代表完整 9.1 GB ISO 已校验。已建立流不会自动迁移或重放；断流的下载由应用重试或续传。

本轮没有在连续测试期间复现真实 ISP 断网，没有证明或排除 QoS，也没有多运营商、长时间持续可用性或真实播放器卡顿率证据。新机制处理可复现的坏连接和协议路径故障，不会使两种路径都被封锁时仍可用。图形界面未进行新的浏览器视觉验收，控制接口使用程序验证。

若面板原来已打开，请刷新后操作；保留自动模式才能使用 H3 备用。手动强制 H2 会禁用跨协议回退。下载仍停在旧连接时，可暂停后继续。
