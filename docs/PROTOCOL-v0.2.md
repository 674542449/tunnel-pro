# tunnelX v0.2 传输策略更新

线上帧格式、鉴权头和 `Tunnelx-Version: 1` 不变，继续使用 [v0.1 协议规范](PROTOCOL-v0.1.md)。本次只更新客户端的传输选择和状态展示；现有 Ubuntu / Debian 服务端可继续使用。

## 选择传输

| 客户端模式 | TCP 请求 | UDP 请求 |
|---|---|---|
| auto，默认 | 首选 H2，失败时尝试 H3 | 首选 H3，失败时尝试 H2 |
| auto，auto_tcp_preference=h3 | 首选 H3，失败时尝试 H2 | 首选 H3，失败时尝试 H2 |
| h2 | H2 | H2 Capsule |
| h3 | H3 | H3 HTTP Datagrams；对端未协商 Datagram 时使用 Capsule |

`auto_tcp_preference` 为可选字段，只接受 `h2` / `h3`，缺省为 `h2`。读取原有客户端配置时即可启用新默认值。该字段由 v0.2 客户端读取；不要把包含此字段的新配置交给严格拒绝未知字段的旧客户端。

自动模式中，连接失败或 CONNECT 响应头建立超时会使该通道进入 30 秒冷却，新请求优先尝试另一种通道。回退仍使用原始隐私模式、ECH 配置、固定 IP 引导和证书校验。证书错误、ECH 拒绝、调用方取消、鉴权或目标拒绝响应不触发业务回退。回退最多建立另一种通道的请求，不发送或重放业务数据。

TCP 和 UDP 可同时复用各自的 H2 / H3 连接。切换模式不会迁移或重放现有流。该策略不包含带宽竞速、动态丢包估计或基于吞吐的连接迁移；已有业务流变慢仍需由应用重新建立连接。

## 加密与性能

TLS 1.3、X25519、AES-GCM / ChaCha20-Poly1305 及 ECH 的 HPKE 套件保持原样。两种通道都验证证书，严格模式必须成功使用 ECH。

H2 的下载使用 Linux TCP 拥塞控制。本次测试节点原先已经启用 BBR 和 fq，本次没有修改全局网络参数。H3 仍使用 quic-go 的 CUBIC。H2 上多个 TCP 业务流共享一条 TCP 连接，外层丢包会阻塞同连接中的流；UDP 优先 H3 避免默认走可靠 Capsule 时的重传等待。

控制面板增加最近成功建立的 TCP 通道。状态接口增加 `tcp_carrier`（0 表示尚无 TCP 请求，2 为 H2，3 为 H3）与 `auto_tcp_preference`；这些信息只描述选择结果，不代表全部既有流已切换。
